# Mod: account auto-router

## What it must do

The user's provider accounts behave like one pool per provider, so they never have to think about which account has room. The router's main job is finishing work already started when an account runs out; it moves as little context as possible.

- **Pools.** Every enabled, signed-in instance of a provider driver is in that driver's pool. Instances that share a config dir (same continuation group key) count as one account. A new instance joins its pool as soon as it is usable. Drivers with one account are left alone (today Codex). The router never changes provider or model.
- **Sticky.** A thread stays on its account while that account has room, because prompt cache lives per account. The router never moves a thread just to rebalance.
- **Failover.** When a thread's latest run fails with a `usage_limit` failure, the router continues it on the best other account in its pool. It uses a manual continuation (`manualContinuationOfRunId`) with the new account in `modelSelection`, so upstream's own provider switch carries the context: a summary of at most 16k tokens the first time the thread visits an account, and a delta when it returns. The message reads "Continue where you left off. (Moved from HDG to EAP: HDG hit its usage limit.)". The thread's waiting plain-text queued messages are re-queued onto the new account in order; messages with attachments or from automations stay as they are. If no other account has room, nothing happens and upstream's resume-at-reset applies. If the run's provider thread had a native `/goal` still being worked on (status `active` or `usage_limited`), the router queues `/goal <objective>` on the new account right after the continuation, because a goal lives in the account's own session and a goal command must run as its own turn (the continuation, not the goal command, carries the context handoff). The old account's session keeps its copy, which only matters if the thread returns there.
- **Returning to an account.** Upstream returns a thread to its old conversation on an account and sends only what it missed, and the provider re-reads that whole conversation. Before any move onto an account (failover or follow-up), the router retires that account's old top-level conversations with the thread when they are at least 100k tokens and their prompt cache has expired (the reported `promptCacheTtlMs`, else 70 minutes, after the latest turn report), or when they have no room for what they missed: the used tokens plus a quarter of the window (at least 16k) plus 16k exceed the window. Upstream's switch skips a retired conversation, so the return starts a new one with a summary, as a first visit does. Without this, a conversation left at 941k of a 1M window failed every turn with "Insufficient context allowance for the provider handoff" (12 Oct 2026); a smaller cold one would have been re-read uncached in full. Retirement is in memory only; once the new conversation exists, it is the account's newest, which the switch prefers anyway. A retire failure is logged and the move goes ahead.
- **Follow-ups.** Before a message starts a turn, an account at or above 90% of its session window, or 97% of a weekly window (including a model-scoped weekly), counts as nearly full. The thread moves to a healthy account if there is one, otherwise it stays. An account the user picked in the composer is honoured while it has room, unless the thread has already left it (it is in the shell's `providerInstanceHistory`): clients keep the account a thread started on, so after a move they keep asking for the old one, and honouring that would bounce the thread back once the old account had room, re-reading its whole old session. Such a request means "this thread's account".
- **Background work stays with its account.** Background subagents, monitors and commands that outlive their turn live in the account's own session; after a move their results never reach the thread. So a follow-up never leaves a nearly full account while its session still runs such work for the thread; it moves once the account is out, when that work stops anyway. When a move does leave work behind (the account ran out, or the user picked another account), the moving message, or the failover's "Continue where you left off", names it so the new account checks what it finished instead of redoing or forgetting it.
- **Stranded wakes.** A provider wake ("Background task completed.") queued for an account other than the one the thread runs on next is cancelled (`queued-run.cancel`) before the message dispatches, and on failover. Started, it would switch the thread back to that account and stop the session it moved to.
- **Composer.** Where the server runs the router with routing on, the composer shows and sends the thread's current account instead of a saved pick of an account the thread left (`apps/web/src/mods/accountRouter/`), so it never shows an account the thread no longer runs on. Upstream's pending handoff preview ("Context handoff pending") reads the same account (`routedPreviewSelection`); reading the saved pick, it announced a handoff in every moved thread that the send never made (15 Oct 2026).
- **Shared config.** Pooled Claude accounts share one user config, so a moved thread keeps what the other account knows. Every 5 minutes the router links each other account's `settings.json`, `CLAUDE.md`, `skills|agents|commands|output-styles/<entry>` and `projects/<project>/memory` to the first config dir (sorted), folding in memory each account kept alone (the newer file wins; the folded-in dir is kept as `memory.unshared-<stamp>`). Account-bound state stays apart: credentials, `.claude.json`, sessions, transcripts and `skills/synced`. A file that differs between accounts is left alone and logged once. It only touches absolute config dirs that exist.
- **New threads** start on the best account: healthy first, then weekly allowance that resets within 24 hours (use it or lose it), then the most session room.
- **Delegated tasks** keep the requested account while it has room, since the caller may have picked it.
- **Imported native sessions, forks, steering and restarts** are never rerouted.
- **Fail open.** Any routing error dispatches the command as sent.
- _Settings › General › Route between accounts_ turns it on or off (on by default) and lists the pooled accounts with a switch each (`accountRoutingEnabled`, `accountRoutingExcludedInstanceIds` in server settings). The server advertises the `accountRouting` environment capability; the row shows only when every environment in the settings scope has it, so a vanilla server never shows a switch that does nothing.

Server code: `apps/server/src/mods/accountRouter/`. `accountRouter.logic.ts` holds every decision as pure functions, covered by `accountRouter.logic.test.ts`. `AccountRouter.ts` applies them. It wraps `dispatch` (rewriting `modelSelection.instanceId` on `thread.create`, `message.dispatch` and `delegated_task.request`), reacts to `run.updated` failures on `streamDomainEvents`, sweeps the shell snapshot every minute for limited threads it missed, and shares pooled Claude accounts' user config every 5 minutes (`sharedAccountConfig.ts`, Node built-ins only). Web code: `apps/web/src/mods/accountRouter/`.

Inputs it relies on: `ProviderRegistry.getProviders` (per-instance `usageLimits.windows`, `continuation.groupKey`, `auth`, `models`) the thread shell (`status`, `lastErrorClass`, `usageLimitResetAt`, `latestRunId`, `providerInstanceId`, `modelSelection`, `providerInstanceHistory`), and thread records (`runs`, `providerThreads[].pendingBackgroundTasks`, `providerThreads[].contextUsage`, `providerTurns[].tokenUsage` (`usedTokens`, `maxTokens`, `updatedAt`, `promptCacheTtlMs`), active `subagent|command_execution|dynamic_tool` turn items, queued runs' `messages`).

## Upstream changes to watch

- If upstream changes what `manualContinuationOfRunId` accepts (today: the latest executed run, `interrupted` or `failed` with class `usage_limit`, `start_immediately`), keep the failover on whatever continuation path accepts another instance.
- If upstream starts carrying native goals across a provider switch, drop the goal re-issue (`goalToCarry`).
- If upstream adds its own cross-account failover or routing, switch this mod off in `mods.json` and drop it rather than running two routers.
- If the provider switch stops being lazy (applied on the next message), placement must still happen before dispatch.
- Claude's continuation group key is `claude:home:<resolved config dir>` (`ClaudeHome.ts`); shared config reads the config dir from it. If that format changes, update `routingPools`.
- If upstream relays a previous account's background results into the thread after a provider switch, or stops a switched-away session's background work, revisit the background-work hold and the stranded-wake cancel.
- If upstream syncs the composer's saved account with the thread's, drop `useRoutedComposerInstance` and `routedPreviewSelection`.
- If upstream itself starts a new conversation when a returning switch's old one is cold or has no room for the delta, drop the retirement (`conversationsToRetire`, `retiredConversations.ts` and its `Orchestrator.ts` hook). If upstream stops picking the target account's conversation in `rootProviderThreadsForProvider`, move the hook to wherever the switch picks it now.
